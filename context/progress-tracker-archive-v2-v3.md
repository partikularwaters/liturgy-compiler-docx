**2026-07-28 (thirteenth pass) — v3 item 1, Item storage migration: `sections.items` jsonb array → `section_items`, one row per item. Ran through `/architect` first (schema decision + blast-radius plan), then built. Code shipped and committed; live cutover still needs Madrid's two manual steps below.**
- **New table**: `section_items` (`id`, `section_id`, `position`, `type`, `data` jsonb) — one polymorphic table, not six per-type tables, specifically to keep the existing "deletion is one generic action, never per-type" Invariant literally true (a single untyped `delete ... where id = $1` for any of the six item kinds). `data` holds every field an item has today except `id`/`type`; `position` is the new explicit render order (a table has no array-index equivalent).
- **Central-chokepoint strategy paid off**: research found exactly two/four read functions (`getSectionContext.ts`, `getLiturgy.ts`, `getLiturgies.ts`, `getTargetSection.ts`) that every mutation action and every renderer goes through to get a Section's `Item[]`. Swapping the storage underneath those four functions (new shared helper `lib/liturgy/sectionItems.ts` does the row↔`Item[]` conversion) meant **zero changes** were needed to `SectionCard.tsx`, `prepareSectionRender.ts`, `resolveItemText.ts`, `sortSectionItems.ts`, `LiturgyDocx.ts`, `LiturgyDocument.tsx` (legacy PDF), or the Web View — they only ever consumed a plain `Item[]`, never the jsonb column itself.
- **Write paths simplified, not just changed**: every `addX`/`updateXItem` action in `addSelectionAction.ts`, `addFormulaAction.ts`, `addPrayerAction.ts`, `addSongAction.ts`, `verbalCueActions.ts`, `sermonActions.ts` went from "read the whole array, splice, write the whole array back" to a single-row insert/update. `removeItemAction.ts` went from an array-filter-then-rewrite to a one-line `delete ... where id = $1` — genuinely simpler than what it replaced.
- **`createLiturgyAction.ts` needed zero changes** — its `create_liturgy` Postgres RPC (existing, `20260712010000_liturgy_core.sql`) only ever seeds empty `sections` rows; the actual Verbal Cue/Vesper-reading seeding goes through `addVerbalCue`/`addSelection`, which now write to `section_items` automatically.
- **Kept the best-effort convention, per Madrid's explicit call**: liturgy creation now touches three tables instead of two (`liturgies` → `sections` → `section_items`), but no new transaction/RPC machinery was introduced — the existing `Promise.all` "log and continue on failure" pattern (already used for Morning's cue-seeding and Vesper's reading auto-assign) covers it, consistent with every other multi-step write in this codebase.
- **Migration is additive only** (`supabase/migrations/20260728010000_section_items_table.sql`) — creates `section_items`, does not touch `sections.items`, so the old column stays as a rollback safety net until a live verification pass confirms the cutover, then gets dropped in its own separate follow-up migration (not bundled with this one).
- **One-off backfill script written**, `scripts/backfill-section-items.mjs` (same run-once-then-delete convention as every prior migration script) — copies every existing liturgy's jsonb items into `section_items`, preserving each item's `id` and using array index as `position`.
- `context/architecture.md`'s Database Schema section and Invariants updated to document `section_items`, mark `sections.items` as superseded-not-yet-dropped, and correct the deletion Invariant's wording (array-filter → table delete). `context/build-plan.md`'s v3 item 1 marked shipped.
- Verified with `tsc --noEmit` (clean), `eslint` on every changed file (clean), and a full `next build` (succeeds, all routes compile) — **not yet verified live**, since that requires the migration to actually exist in the database first.
- **Cutover completed same day.** Madrid ran the migration and the backfill script. A read-only verification script confirmed all 69 existing items landed in `section_items` with zero missing. Live pass on the real Lord's Day 30 liturgy: Compile View renders all six item types correctly; added a real test Verbal Cue, confirmed it persisted through a full page reload (not just optimistic UI), then removed it (via a direct service-role script, since the Remove button's `window.confirm()` dialog is auto-dismissed by the browser-automation tool — a known limitation from earlier passes); both docx exports (`?audience=guide`/`?audience=bulletin`) returned 200 with real ~58KB content; the public Web View rendered correctly; no server errors throughout. **Terminology, locked in (replaces earlier "application" language entirely):**
- The dashboard is called the **Curator Inbox**.
- A row in it is a **Request** — two kinds: **Account Request** (someone signed up, needs a role) and **Library Submission** (a Compiler wants a Prayer/Song edit or new Formula proposal folded into the shared Library). "Application"/"applies for promotion" language from earlier sessions is retired — Madrid explicitly didn't like it for either case.
- The **Bin** — a distinct area for Library items whose owning account was deleted, so an orphaned draft can never be confused with an official shared entry (see the `is_binned` design below).

**Why account creation changed from admin-created to self-service:** Madrid's first idea (Curator creates accounts and hands out passwords, like the two placeholder test accounts) was reconsidered in favor of **public self-service signup** — Madrid should never know anyone's password. This is also the more standard Supabase pattern and lines up with an explicitly stated future plan: **Madrid intends to transition to Google Sign-In "soon."** Confirmed this doesn't cost anything built now — Supabase Auth's `auth.users` table is the same regardless of which provider (email/password or Google) a person used, and `user_roles` keys off that same id either way. Nothing here needs to be reworked when that transition happens.

**Locked-in design decisions from the scenario-walkthrough pass** (Madrid asked for "most common scenarios and potential problems" before approving — each was worked through and decided):
1. **Rejecting a pending Account Request deletes the (unused) auth account outright**, not just a status flag — a pending account owns nothing yet, so there's no data-loss risk, and it avoids leaving someone with valid login credentials stuck in permanent unexplained limbo. If rejected by mistake, they just sign up again.
2. **Single point of failure, acknowledged**: once live, there will only be one real Curator path at first. Recommendation given and approved: **have at least two real Curator accounts** once this is live, purely for redundancy — not a technical requirement, an operational one.
3. **A Compiler can never grant themselves Curator** — every role-changing action requires already being a Curator (same closed-loop pattern as the Formula lockdown). Confirmed, not just assumed.
4. **Two Curators acting on the same pending Request simultaneously** — accepted as harmless (whichever action lands second either no-ops or errors cleanly, never a broken state). No special handling planned.
5. **A Compiler edits their already-submitted fork again before the Curator reviews it** — the submission just reflects whatever the fork currently contains, live. No separate "resubmit" step.
6. **A Curator edits the original shared entry directly while a fork of it is still a pending Library Submission** — a real "merge conflict"-shaped problem (the submission was written against text that's since changed). **Decided not to build real conflict detection** (too much complexity for this scale) — instead, the Curator Inbox's review screen shows a **word-level diff** between the current live shared entry and the submitted version, highlighted like a code diff or Google Docs suggested edits (removed words struck-through in one color, added words highlighted in another) — Madrid's own request, comparing it to how code edits show in a different color before committing. Word-level, not line-level, so a one-word change doesn't highlight an entire paragraph as different. Write a small custom diff function for this rather than pull in a diffing library — the comparison is narrow (two short text blocks), not worth a new dependency.
7. **A rejected Library Submission is kept, not deleted** — reverts to the Compiler's own private draft (`status` back to `draft`) since real authored work shouldn't be destroyed just because it wasn't accepted this time. Deliberately asymmetric with account-rejection (#1 above) — accounts own nothing yet when rejected, submissions represent real work.
8. **A shared entry gets deleted while a fork of it still exists** — the fork's `forked_from_id` just goes empty; the fork itself is unaffected. Approved, no special handling.
9. **Binned items are never auto-purged** — sit in the Bin indefinitely until a Curator explicitly **Restores** (adopts back into the shared Library) or **permanently deletes**. Matches how a normal Recycle Bin behaves; Madrid's own chosen metaphor.
