- **2026-07-13, follow-up round — the first marker restyle was still wrong, plus two real UX gaps caught by driving the app directly:**
  1. **`rounded-md` on a 16px box is a circle, not a square.** This project's `--radius-md` token is 8px — exactly 50% of a 16px box, so "light gray square with rounded corners" rendered as a plain circle. Switched to `rounded-sm` (4px = 25% of the box) — confirmed via computed styles in-browser (`borderRadius: "4px"` on a 16×16 box) that it now actually reads as square. **Lesson: when sizing a rounded corner relative to a small fixed box, sanity-check the radius-to-size ratio, not just "which token sounds small."**
  2. **Compile-mode context was invisible and had no way back.** Beyond one muted hint line, the Reader looked identical to plain browsing, and the sidebar still highlighted "Bible Reader" — actively misleading, since you were still inside the Liturgy workflow. Fixed with a persistent `bg-accent-light` banner ("Compiling: {template} → {section}" + "← Back to Liturgy" link to `/liturgy/{id}`), and by splitting `Sidebar.tsx` into a `SidebarLinks.tsx` client component (using `useSearchParams` to detect `liturgyId` and highlight "Liturgies" instead of "Bible Reader") wrapped in `Suspense` — necessary because `useSearchParams` in a root-layout component forces every page to need a Suspense boundary or the build fails (`next build` caught this immediately: "useSearchParams() should be wrapped in a suspense boundary").
  - Madrid also asked directly whether the Reader should live under `/liturgy/[id]/reader` instead of `/reader?liturgyId=...` — considered and explained the trade-off rather than building it: query-param context plus the banner/back-link/sidebar fix addresses the actual complaint (disorientation, no way back) without the cost of either duplicating Reader logic across two routes or making `/reader` itself a conditional/nested path. **Madrid confirmed: keep the lighter fix, revisit the nested-route idea in a later phase if needed — not now.**
- **2026-07-13, another follow-up round — marker still too subtle, plus a real state-management bug found while adding the last piece:**
  1. **Marker bumped up and given real color-coded states**, per Madrid's spec: `w-4 h-4` → `w-5 h-5`, `font-normal` → `font-bold`, `text-[10px]` → `text-[12px]` (was "too thin, hard to recognize"). States now use actual background color, not just tinted text on gray: `pending` is a solid `bg-error` (red) box — "the state after you click +, if you want to remove it"; `saved` is a solid `bg-success` (green) box — "already added." `addable` stays the neutral gray box.
  2. **Added a success confirmation** — `bg-success-light` bar reading "Successfully added to {section}" beneath the existing `bg-accent-light` "Compiling: …" banner, appearing right after a Selection saves.
  3. **Real bug caught while wiring #2 in:** the success message vanished immediately after appearing. Root cause: the `useEffect` resetting per-chapter Reader state depended on `initialHighlights` (an object prop), which gets a fresh reference on every `router.refresh()` — including the refresh `handleSaveSelection` itself triggers right after setting the success message. That refresh re-fired the effect, which unconditionally set `successMessage` back to `null`. Fixed by dropping `initialHighlights` from the effect's dependency array — it should only reset on an actual `chapter.book`/`chapter.chapter` change, not on every data refresh within the same chapter. **Lesson: an object/array prop in a `useEffect` dependency array will retrigger on every parent re-render that produces a new reference, even with identical content — this is exactly what `router.refresh()` does to every prop passed down from a Server Component. Watch for this pattern anywhere a `useEffect` depends on a non-primitive prop.**
